# 005 — Docker Compose runtime

## Purpose

Deploy a source-defined Compose project, including source builds, while preserving exact deployment artifacts for rollback.

## Scope

Docker Compose v2 and a local Docker daemon on Linux. Compose source builds are part of the v0.1 MVP. The maintainer-approved decisions are local source builds without an optional BuildKit feature dependency, capability-based preflight, existing Docker credentials, retained actual image content, bounded private-artifact cleanup, and conservative rollback/storage admission checks. Isolated per-attempt workspaces do not isolate the shared daemon. This specification revision awaits maintainer review before implementation.

## Requirements

### Identity, context, and input validation

- The endpoint MUST be `unix:///var/run/docker.sock`. Ambient contexts and DOCKER_HOST MUST NOT select another daemon. Save and compare daemon identity before artifact operations or workload mutation. Ownership MUST bind the canonical installation, Application, daemon, and exact project `pulltide-<metadata.name>`. Reject preexisting unowned projects before reserving ownership or changing resources.
- Invoke Compose with explicit files in declaration order and the selected source directory as working/project directory. Follow Compose's documented resolution rules for included projects and Dockerfiles; resolve every resulting definition/context path to a retained repository input. Do not rewrite nested relative paths blindly against the top-level directory.
- Compose resolution and workload settings use only `PATH=/usr/bin:/bin`, `LANG=C`, the explicit endpoint, and tracked dotenv inputs rooted in the retained repository. Docker control operations have the narrow external credential-access exception below; it MUST NOT alter these resolution/workload inputs. Top-level interpolation uses the selected source directory's tracked `.env`, or an explicit empty dotenv input. Nested included dotenv files must be explicitly resolved and retained; no host/parent-directory discovery or unvalued environment passthrough is allowed. Deployment environment values must be explicit after resolution.
- Before any build, pull, or workload mutation, validate the full transitive input closure: Compose files, include/extends, dotenv/env_file, file-backed configs/secrets, build contexts, Dockerfiles, and applicable ignore files. Follow dependencies into sibling directories inside the repository. Apply [Git unsupported-content validation](003-source-git.md) to every referenced file and every entry of an accepted context, even when ignored by the builder. Missing, untracked, remote-definition, escaping, cyclic, gitlink, or LFS-pointer inputs MUST fail preparation. Paths containing `..` in nested driver references are permitted only if their final resolved locations remain inside the retained repository; top-level Application paths retain the stricter rules in 001.
- Source/definition confinement does not cover operator-managed external application data or host executables. External bind-mounted data paths are allowed if accessible, but are neither retained nor restored. They MUST NOT supply build contexts, Dockerfiles, dotenv, or other deployment definitions. Named-volume data likewise remain external state.
- Explicit `container_name`, external shared networks/volumes, and explicit network/volume `name` overrides are unsupported; project-scoped resources are allowed. Operators MUST NOT modify Pulltide-owned image aliases, resources, or inputs concurrently. Pulltide does not fence arbitrary host administrators.

### Engine and Compose capability preflight

- Require a reachable local Docker Engine and a positively identified Compose **v2** CLI. Record observed versions, daemon identity, native platform, and capability results as nonsecret compatibility evidence. Do not infer safety from a guessed minimum Engine/Compose/BuildKit version. The version strings are evidence, not a substitute for capability checks.
- Before artifact operations, verify executable accessibility, negotiated Engine API access, daemon/platform/ownership identity, and installed command support for parsing/merging the requested Compose files, local builds, image inspection/export/import, project-scoped cleanup, and application with both build and pull disabled. Use bounded nonmutating CLI/API discovery and validation first. Actual build/pull/export/import outcomes must still be checked and journaled; advertised capability is not a guarantee that an operation will succeed.
- Baseline context-plus-Dockerfile builds MUST NOT require BuildKit-only flags, Buildx/Bake selection, attestations, provenance, SBOM, secret/SSH mounts, or other optional BuildKit features. Pulltide neither forces nor disables a backend solely because it is called BuildKit; use the installed local Engine's working build path. If that installed path requires a missing component even for a baseline build, report that exact capability failure without claiming all v0.1 installations require that component.
- Check additional capabilities only when requested by the accepted input: for example inline Dockerfiles, a target stage, explicit build network options, or nested includes. An unsupported requested option fails preparation before builder invocation/workload replacement; its absence MUST NOT reject a plain supported build. No unconditional inline-Dockerfile or advanced build-feature probe may gate baseline builds.
- Complete source/dependency validation and existing rollback-artifact/storage admission below before any mutating capability exercise. Do not start test services or mutate the current project to probe compatibility. Missing/inconclusive required capabilities fail with a sanitized preparation category; installed version/help output alone cannot promote an artifact or deployment.

### Existing Docker credentials

- For private registry pulls and private base-image access, use the dedicated service account's existing Docker configuration: its externally configured `DOCKER_CONFIG` directory, otherwise the account's normal `$HOME/.docker` directory, including configured credential stores/helpers. Select that location once per process startup, independently of repository dotenv or Compose settings. Do not perform login/logout, prompt interactively, copy that configuration into Pulltide state/workspaces, or create Pulltide-owned credential files.
- Credential use is confined to Docker control operations and their authentication/helper channel. The controlled environment may supply the service account's HOME/configuration path and the minimum external session context needed by its already configured helper, solely for authentication. No arbitrary parent build/Compose/proxy/context variables are inherited. Required helpers must be accessible and noninteractive in that account's environment; unavailable helpers, locked stores, denied access, expired credentials, and registry rejection are classified preparation failures before replacement. Anonymous/public builds must not require a logged-in account or an existing credential file.
- Existing Docker configuration may contain non-authentication settings. Explicit endpoint/builder selection and pre-resolved build/deployment inputs MUST prevent that file from selecting another daemon/builder, injecting proxy build arguments, or changing application interpolation/environment. If installed tooling cannot consume authentication without applying conflicting settings, reject preparation with a sanitized reason rather than copying credentials or silently accepting the change. Within Pulltide, helper output and registry auth/session material may exist transiently only; they MUST NOT be placed in logs, status, state/journals, manifests, generated descriptors, build arguments, image archives, or a context supplied by Pulltide.
- Resolve inputs before exposing this authentication channel to Docker. Workload containers and command health checks do not inherit the account's HOME, DOCKER_CONFIG, helper context, or credentials through this exception. Store only nonsecret artifact/version/identity evidence. Operators MUST NOT embed registry credentials in Dockerfiles, Compose arguments, or tracked dotenv; Pulltide supplies no secret-build-argument mechanism and cannot sanitize arbitrary operator code that deliberately bakes a secret into an image. Registry availability/credentials are not rollback inputs: retained offline restoration never invokes a registry or credential helper.

### Build preparation and isolation limits

- Preparation MUST validate and prepare all service images before stopping or replacing any running service. No `up`, service creation/start/stop, orphan removal, volume deletion, or project teardown may occur during preparation. Build/pull/import can change daemon images/cache and consume host resources; the guarantee is preservation of managed workloads, not a side-effect-free Docker daemon.
- Both `build: <relative-context>` and mapping form MUST be supported. The accepted mapping profile permits `context` (default `.`), `dockerfile` (default `Dockerfile` only when no inline Dockerfile is supplied), `dockerfile_inline` (mutually exclusive with dockerfile), explicit string-valued `args`, `target`, `labels`, `no_cache`, `pull`, and `network` (`default` or `none`). Use one native Linux platform, captured in the artifact manifest. Options beyond the ordinary context/Dockerfile path are capability-gated only when explicitly requested. Validate types against the selected Compose implementation; no optional BuildKit feature is an unconditional prerequisite. Null/unvalued build arguments and interactive prompts are rejected. An `image` attribute alongside `build` MUST NOT cause a registry pull to bypass the source build: build output is authoritative and any source tag is only an input label, never the deployable identity. Override output names before invoking the builder with private aliases unique to Application, attempt/instance, and service; B preparation MUST NOT retag A or user images.
- Local contexts and Dockerfiles MUST come from the validated immutable snapshot, with a unique isolated workspace/staging area for each attempt and separate instances for restoration. This isolation separates files and output names only; daemon caches, storage, CPU, network, and builder processes remain shared. No default build operation may read an active instance's mutable workspace. Local contexts and Dockerfiles use private staging for builder access. Runtime workspaces and ambient host files MUST NOT enter a context. Capture the actual build arguments, target, context/Dockerfile/ignore hashes, builder identity/version, native platform, and image IDs. Mutable base tags and Dockerfile network downloads are allowed as external build-time dependencies; identical Git/config targets need not rebuild to identical bytes. The retained output, not a reproducibility claim, is authoritative.
- Use the local daemon's build facility; do not select a remote or ambient named builder. Requested privileged builds, insecure entitlements, host networking, SSH agent forwarding, host secret mounts, external/additional contexts, and explicit cache import/export destinations are rejected in this initial profile. Normal daemon-managed cache is allowed. Unknown build options fail before invoking the builder, never silently ignored. These bounds retain ordinary local builds without requiring optional BuildKit features; extending the profile requires a reviewed specification change.
- Default build networking may access registries, package servers, or other reachable endpoints. Dockerfiles, any selected Dockerfile frontend, and builder inputs are trusted operator code. Dockerfile network downloads and remote ADD inputs are external build-time dependencies, not permitted alternative host/remote Compose definitions or contexts. Path checks and denied entitlements do not guarantee network isolation, host isolation, resistance to malicious builds, resource quotas, or reversal of external side effects. A build can exhaust shared disk/CPU or affect service availability indirectly. Pulltide MUST NOT advertise builds as a security sandbox. Registry authentication uses the existing configuration as specified above. Default build networking and the shared daemon are explicit v0.1 limitations; stronger isolation is outside this MVP, not an implied guarantee.
- Core MUST durably journal each potentially asynchronous artifact operation before invocation, including build, pull, and import, with operation/boot identity and target. Every such operation is bounded by the attempt's frozen operation timeout plus at most ten seconds for client termination. Client death/nonzero exit/timeout does not prove daemon completion. Unknown completion blocks further builds, checks, and deployment until quiescence; it does not trigger rollback or failed-target suppression when no workload-mutation intent exists. Shutdown leaves that preparation journal for restart handling in 007.

A supported source-build example in a repository's `deploy/compose.yaml` follows. This is a Compose file, not an Application document; `../app` must resolve to retained sibling source inside the same repository:

```yaml
services:
  web:
    build:
      context: ../app
      dockerfile: Dockerfile
      args:
        BUILD_MODE: release
```

### Immutable deployment artifacts and rollback inputs

- For every service, preparation MUST produce a manifest entry with exact local image ID, platform, and a checksum-verified durable image archive sufficient to reload that same image on the owned daemon. Image-only services must name a digest-pinned image; resolve/pull it during preparation and archive the resolved native image too. Built services need no registry digest or publication: local image IDs identify their actual outputs.
- Export archives to explicit private artifact files, not diagnostic stdout; an archive is a typed binary artifact, never retained command-output logging. Export without overwriting user image tags. Retain only Pulltide-owned aliases in archives, or no aliases; import MUST NOT overwrite unrelated host aliases. Archive publication, checksums, image-ID verification, resolved configuration, source inputs, and directory metadata MUST be durable before a manifest is marked complete or a deployment journal references it. Interrupted/incomplete outputs remain ineligible. The daemon cache alone is not rollback retention.
- Render a private deployment descriptor from the resolved configuration: remove build directives, remove source image/pull policies, bind each service to the exact retained image (using a private alias if necessary), and disable build/pull. Verify alias-to-image mappings before use and verify actual container image IDs after apply. Unexpected IDs fail verification and invoke the shared failure policy. Artifact identity is `artifact-v1:` plus the lowercase SHA-256 hash of manifest bytes encoded with 001's canonical JSON rules. The versioned manifest contains workspace-relative descriptor-template/input hashes, platform, exact image IDs, and archive byte checksums. Instance-specific absolute paths and private aliases are separate binding records, not changes to the immutable template. Archive byte checksums are integrity evidence, not a claim that repeating export/build produces identical archive bytes. Core treats this driver artifact identity as opaque and separate from source/config target identity.
- Apply and restore MUST have the semantics of `docker compose up --detach --remove-orphans --no-build --pull never` over the retained descriptor. Neither may reevaluate source build or resolve a mutable image tag. Reload missing images from verified retained archives in a separately journaled artifact operation before workload mutation. A missing/corrupt archive or unsupported import blocks recovery; it MUST NOT fall back to rebuilding or pulling.
- Retain snapshots, build contexts/metadata, resolved descriptor, image manifests/archives, and workspace references while active, last-good, or pending records reference them. Builder caches and mutable upstream dependencies need not be retained because rollback uses the saved outputs. Cleanup MUST NOT delete retained archives or images referenced by another deployment. Automatic global Docker/image pruning is forbidden.
- Restoration creates a fresh workspace and unique deployment instance using last-good's existing image manifest. Rebinding retained definition paths to that workspace creates a new instance descriptor; it MUST NOT change resolved service settings or image IDs. Atomically publish the restored instance/workspace references as required by 007.

### Retention, rollback admission, and storage

- Pin the latest verified last-good deployment's required source/configuration, recovery workspaces, resolved descriptor, manifests, and actual image archives, plus a candidate's partial/complete artifacts throughout its active attempt. Preserve prior/candidate/restoration operands while a journal may need them, including after a failed or uncertain operation. Active/last-good may share immutable blobs; references from another Application or instance are still live. There is no extra successful-revision history: after a durable promotion, recovery, or cleanup transition releases the final reference, old inputs become eligible for bounded reclamation under 007. Historical last-good remains pinned even if active is absent after disabled rollback cleanup.
- Before build, pull, or import can change daemon state, verify all already-required rollback artifacts under canonical ownership. Recheck immediately before each managed-workload mutation and before each recovery mutator. Verify manifest/source/configuration integrity, full archive readability and checksums (not just file existence), expected platform/image identities, descriptor/input availability, and the saved operands needed for cleanup. A valid daemon image cache MUST NOT excuse a missing/corrupt retained archive. Reuse a validation result only while the same immutable content is pinned and its integrity evidence remains valid. For a first deployment with no last-good, that set is explicitly empty; candidate completeness is still mandatory before apply.
- Guard failure before workload mutation preserves the running instance, reports preparation failure, and creates no failed-target suppression. Guard failure during pending recovery preserves its journal and enters recovery-required without another mutator. Never rebuild, pull, or release a protected artifact to make the guard pass. Validation and any recovery imports are within the frozen timeout/budget in 008; an oversized or inconclusive check may fail safely rather than be skipped.
- Check writable/free capacity and inodes on every relevant local filesystem: canonical state/artifact store, attempt/export staging, and the daemon/builder's reported storage locations. Where a shared filesystem backs several locations, count pending writes together once. Use current free space available to the operating account, actual known sizes of pending copies/archives/imports, and at least 16 MiB and 32 free-inode headroom for metadata/state on each filesystem. If available capacity/inode counts on a required filesystem cannot be measured or a known write lower bound plus headroom does not fit, fail preparation conservatively before starting that work. Unknown build/layer/export expansion cannot be assigned a reliable total size; record only an inconclusive estimate, never a capacity guarantee.
- Repeat storage checks before each sizeable artifact operation, before replacement, and before recovery. A passing check is not a reservation, quota, or promise: shared-daemon activity, compression expansion, inode exhaustion, permissions, device failure, and concurrent writers can invalidate it. Every write/export/import and durable commit must check its actual result. On ENOSPC, quota failure, or short write, do not publish an incomplete archive or replace services with unretained outputs. If workload mutation already occurred, stop dependent actions; recover only when storage, artifacts, and quiescence permit, otherwise retain recovery-required evidence. Do not delete protected rollback content to recover capacity.
- Automatic reclamation is bounded private-file cleanup as specified in 007. It may remove abandoned staging and unreferenced archives/workspaces only after durable release. It MUST NOT run Docker system/image/builder prune, remove daemon images by ID, delete volumes, or remove unrelated aliases. Daemon cache and obsolete private image aliases are operator-managed; they may accumulate even after Pulltide's file references are released. Operators may reclaim daemon storage separately, but retained readable archives remain required for offline restoration. Retention limits deployment generations, not bytes: a large active/candidate set or failed cleanup can exhaust storage and must fail safely rather than promise a fixed disk footprint.

### Operation results and cleanup

- All recovery operations use the pending attempt's frozen timeout, regardless of the prior/restored operand's historical timeout. Saved operands supply configuration/images/workspace, not timeout policy. Startup health uses its saved observation policy instead.
- Outcomes are `completed-success`, `completed-failure`, or `completion-unknown`. Successful client completion must be accompanied by valid operation-specific completion evidence; failure is completed only when no daemon mutation remains. PID absence, current containers, or passing health alone are insufficient. A changed host boot identity establishes termination of prior local processes, but daemon/resource/artifact validation is still required; a restart of Pulltide alone is insufficient.
- Cleanup MUST remove all owned project services/networks across prior, candidate, and interrupted restoration configurations, including orphans. Confirm no owned services remain before reporting absent. Preserve named volumes, unrelated projects, and retained rollback artifacts. Runtime file mounts may use the mutable workspace; persistent data must tolerate workspace replacement.
- A build error with confirmed completion leaves the prior deployment unchanged and may retry on a later poll; an uncertain build blocks until safe restart recovery. A failed apply follows frozen rollback policy only after quiescence. A failed restoration leaves active unknown and last-good historical.

### Resolved decisions and explicit limitations

The seven approved decisions are normative in the sections above. There is no unresolved prerequisite design question for baseline v0.1 local builds: use capability checks instead of guessed version floors, external Docker credential facilities, actual retained image content, bounded private-file reclamation, and conservative artifact/storage guards. Optional advanced build features, multi-platform output, stronger daemon/build isolation, restricted egress, automatic shared-daemon pruning, and credential provisioning remain excluded extensions. They must not become hidden prerequisites or reasons to remove ordinary source-build support. The detailed amendments still require maintainer review before implementation.

Docker references supporting the underlying command capabilities: [Compose build](https://docs.docker.com/reference/compose-file/build/), [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/), [image save](https://docs.docker.com/reference/cli/docker/image/save/), and [image load](https://docs.docker.com/reference/cli/docker/image/load/), [Docker CLI configuration](https://docs.docker.com/reference/cli/docker/), and [registry credentials](https://docs.docker.com/reference/cli/docker/login/). Pulltide's retention and safety requirements above are its own contract.

## Non-goals

Swarm, Kubernetes, remote daemons/builders, multi-platform publishing, general CI pipelines, untrusted-build sandboxing, volume snapshots, and database migration reversal. Image builds are explicitly in scope.

## Failure behavior

Invalid dependency closure, build profile, ownership, or context fails before invoking builds or changing managed workloads. Confirmed build/export failure preserves active/last-good and never promotes partial artifacts. Missing/inconclusive capabilities or unusable registry authentication fail preparation; credentials are never retained or echoed. Storage exhaustion blocks publication and workload replacement; estimates never bypass actual write/durability errors. Artifact-cleanup failures leave remaining backlog for later bounded batches and do not permit protected deletion. Uncertain daemon work preserves its journal and blocks all competing operations. Missing retained rollback images are restored from archives; missing/corrupt archives block instead of rebuilding. Build network side effects and resource contention are outside rollback guarantees.

## Acceptance criteria

- **COMPOSE-01:** Revisions and rollback use one owned project; preexisting unowned projects and daemon mismatches reject mutation.
- **COMPOSE-02:** Validate all sibling/nested references and entire accepted build contexts before builder invocation. An LFS pointer in a sibling env file or context fails; external application data is allowed while an external Dockerfile/definition is rejected.
- **COMPOSE-03:** Parent Docker/Compose variables do not change endpoint, interpolation, workload/health environments, inputs, or builder. Only the explicit credential-configuration/helper exception reaches Docker authentication. Explicit source build with `image: mutable-tag` still builds source and deploys its recorded output.
- **COMPOSE-04:** Partial update cleanup removes old/candidate orphans, preserves named volumes/unrelated resources/retained artifacts, and verifies absence.
- **COMPOSE-05:** Build A then B, fail B health, change base tags and remove daemon image cache: rollback reloads A's archives and runs exactly A's image IDs with zero build, pull, or Git calls.
- **COMPOSE-06:** Kill the client during build/import/apply or delay daemon completion past timeout. No competing operation begins without proof; preparation-only interruption does not suppress the candidate or stop A.
- **COMPOSE-07:** Missing/corrupt archives, export interruption, and disk full prevent manifest publication/replacement. Recovery never substitutes a fresh build or network image.
- **COMPOSE-08:** Both context-string and mapping Dockerfile/args/target builds work; all images finish and are durably archived before the first service mutation. One failed service build leaves every current service unchanged.
- **COMPOSE-09:** Escaping contexts, unsupported entitlements/SSH/secrets/additional contexts, host networking, and unvalued args fail before builder invocation. Default network builds may fetch dependencies; docs and status make no sandbox/reproducibility guarantee.
- **COMPOSE-10:** Generated descriptors disable building/pulling; observed image IDs equal the retained manifest. Rebinding restoration workspace paths preserves manifest images/settings and updates instance references atomically.
- **COMPOSE-11:** Referenced archives survive artifact GC; import never changes unrelated image aliases. Repeated preparation after no workload mutation may produce different output IDs without changing target eligibility rules.
- **COMPOSE-12:** A capable Engine/Compose v2 setup with optional BuildKit features absent can complete a plain context/Dockerfile build, archive, apply, and offline restore. No mandatory advanced flag/inline/attestation probe is issued. If the installed baseline path lacks a required component, report the demonstrated capability failure, not an invented version floor.
- **COMPOSE-13:** Missing Engine access, non-v2 Compose, missing export/import or no-build/no-pull support, and unsupported explicitly requested optional input fail before workload mutation. Actual artifact-operation errors cannot be converted into success by a version/help check.
- **COMPOSE-14:** Private image and private base-image access use an existing config/helper with a fake credential marker. No login/provisioning occurs; marker appears in none of state, journal, context, manifest, archive, status, or logs. HOME/config/helper context is absent from workloads/checks; conflicting non-auth Docker settings are rejected or conclusively neutralized.
- **COMPOSE-15:** Locked/missing helpers, expired/rejected credentials, and unreachable registries fail preparation without replacing A or suppressing the target. An anonymous public build does not require a config file. Offline rollback with registry/helpers unavailable loads the saved images without any authentication/network request.
- **COMPOSE-16:** During A-to-B, A remains pinned through builds and uncertain B. Durable success of B makes only unreferenced A inputs eligible; shared and pending inputs remain pinned. Interrupted deletion/restart cannot remove B or another Application's shared blob.
- **COMPOSE-17:** A larger-than-batch backlog, failed unlink, and elapsed cleanup budget schedule no extra batch in the same cycle. At most 128 private filesystem entries and min(5 seconds, frozen/current operation timeout) of scheduling occur; no daemon prune/image-ID deletion or protected file deletion is invoked.
- **COMPOSE-18:** Delete/corrupt a required A archive while A still exists in daemon cache: rollback admission fails before any B build/pull/import or service replacement. Delete it during pending recovery: no next mutator, no rebuild/pull fallback, recovery remains blocked.
- **COMPOSE-19:** Fake low/unknown capacity, low inodes, and shared-path accounting exercise the known-write lower bound plus 16 MiB/32-inode margin. A passing estimate followed by ENOSPC/short write never publishes artifacts or success; after mutation it blocks dependent actions and preserves recovery evidence.
- **COMPOSE-20:** Per-attempt source/build workspaces and aliases differ, but shared daemon cache/resource pressure is observable and explicitly outside isolation guarantees. Automatic local cleanup does not imply bounded daemon storage or a fixed total disk footprint.
