# 004 — Exec runtime

## Purpose

Deploy applications through operator-supplied local commands with a defined lifecycle.

## Scope

Exec preparation, replacement, cleanup, restoration, observation, execution context, timeouts, and recovery compatibility on the local Linux host.

## Requirements

### Execution and lifecycle

- `apply` and `stop` MUST be nonempty argument arrays executed without an implicit shell. Operators may explicitly invoke a shell. Preparation MUST validate the working directory and executable accessibility before stopping the prior deployment.
- Commands MUST run in the deployment's retained mutable workspace at its configured source path. The environment MUST contain only `PATH=/usr/bin:/bin`, `LANG=C`, and the saved `exec.env` overrides; no host environment is inherited. Executable lookup uses that effective PATH. The same saved context MUST be used during cleanup, restoration, and command health checks.
- The immutable source snapshot and mutable workspace MUST be separate. Commands may write their workspace but MUST NOT modify the immutable snapshot. Files needed by stop or health MUST remain in that retained workspace. Restoration MUST create a fresh unique deployment instance/workspace from last-good's immutable snapshot; allocate and durably record it before apply. An interrupted restoration retains its own instance/operand for cleanup. Success atomically binds active and last-good to the restored instance as specified in 007. Source/definition confinement does not prohibit explicit host executables or operator-managed external application data; those are not retained source inputs.
- For replacement, preparation MUST complete before the prior deployment's stop begins. That stop MUST complete successfully before candidate apply. First deployment has no prior stop. Core reconciliation owns intent recording and policy; the driver returns outcomes and MUST NOT promote last-good or independently initiate rollback.
- Apply MUST finish after arranging the application's long-running service through an operator-provided mechanism. Pulltide is not a service supervisor. Deployment mutations MUST finish within the command lifetime: commands MUST NOT leave background deployment scripts, remote deployment jobs, or scheduled deployment mutations running after return. A long-running application service is permitted, but it MUST NOT continue unfinished deployment work.
- Operators MUST supply idempotent apply and stop commands. Stop MUST tolerate an already-stopped or partially applied deployment and complete removal of the owned workload. Apply MUST tolerate replay after quiescence has been established. Command success cannot prove arbitrary scripts meet these obligations; these are operator responsibilities.
- Commands MUST publish generated stop/health recovery files crash-safely and tolerate missing/partial files after interruption. Before durable completion or a dependent action, Pulltide synchronizes the owned workspace and directories under 007; failed synchronization blocks advancement. Running application data and external paths are not transactionally snapshotted.
- Cleanup MUST use the configuration and workspace of every deployment whose apply may have started. A previous stop that may have started MUST be finished before restoration. Restoration applies last-good only after required stops complete successfully, then uses last-good health checks. Stop failure prevents any further apply.
- Zero exit status indicates operation success; nonzero exit or launch failure indicates failure. Apply success alone never establishes deployment health. Stop success means absent only for conforming commands that satisfy the complete-removal obligation.

### Foreground process profile (approved v0.1 decision)

Exec supports trusted, foreground, process-group-contained commands only. The operator MUST explicitly attest this profile and the existing canonical ownership binding when wiring the internal adapter. This attestation is not a new Application field or automatic resource adoption. Every deployment/check descendant MUST stay in the launched process group and finish within the foreground command lifetime. Detaching/session escape, unmanaged background mutators, remote jobs, and returning before an external mutation completes are unsupported. Long-running application services MUST be managed externally, for example through a synchronous systemd operation that finishes its deployment job before returning. The supervisor does not infer conformance by parsing shell code or executable names.

Completion combines the foreground exit result with observed termination of its supported process group. It is conditional on the operator's foreground/local-only contract, not proof about escaped descendants or arbitrary external systems. A group that still has running members after its foreground process exits violates the profile: attempt bounded group termination but return completion-unknown, even if that cleanup subsequently succeeds. Unreadable/inconclusive process evidence, unsuccessful termination confirmation, or observed unsupported/external completion uncertainty also returns completion-unknown and blocks further commands. Process-group emptiness MUST NOT be advertised as general descendant containment or external mutation quiescence. Stronger cgroup/systemd containment is future work. After process death, this adapter supplies no same-boot quiescence proof; the existing 002/007 restart barrier applies.

Cancellation uses the same group termination protocol as timeout. A command cancelled before launch is completed-failure without invocation. Normal foreground children are permitted while their parent waits for them. Zombies are not running mutators; unreadable required process metadata is inconclusive. TERM starts at cancellation/timeout, KILL follows after at most five seconds, and confirmation stops after at most five further seconds. Signalling/observation failures cannot manufacture confirmed termination. Raw process output never supplies completion evidence.

### Generated recovery inventory (approved v0.1 decision)

Every successful apply, including restoration apply, MUST freshly publish `.pulltide-exec-recovery.json` in its selected source working directory. This is a Pulltide-controlled reserved filename, not a public Application setting or an extra inherited environment variable. The source-selected subtree MUST NOT contain a tracked entry with that name at its selected root. Before apply, the adapter removes a prior regular inventory from this fresh attempt's workspace; symlink/nonregular inventory paths fail before invocation. Stop and health commands MUST NOT rewrite the inventory. A valid empty inventory explicitly declares that no generated recovery inputs are required; the adapter cannot verify that claim by interpreting arbitrary commands. Commands needing generated stop/health inputs MUST list them.

The exact closed JSON shape is `{"version":1,"files":["workspace-relative/path"]}`. Version is integer 1. Both fields are required; unknown fields, duplicate JSON keys, duplicate paths, malformed/trailing JSON, and inventory content over 1 MiB fail validation. Paths are nonempty canonical Linux workspace-relative file paths: no absolute paths, dot/dot-dot components, NUL, reserved inventory self-entry, symlinks in any component, nonexistent entries or unsupported file types. Inventory and listed files MUST be readable regular files owned by the operating UID, with one hard link, no group/other write permissions and no special mode bits. Traversed directories MUST be owned by that UID and not writable by group/other. The canonical private workspace root remains mandatory. Error messages MUST NOT include inventory paths or contents.

Commands publish the inventory atomically and crash-safely after the listed files are complete. The adapter verifies every entry, synchronizes inventory/files and their containing directories, and returns the inventory's workspace-relative path plus all listed paths in `Result.RecoveryFiles` only after successful foreground completion and successful validation/durability. Core alone records those references in the journal/state and synchronizes the owned workspace. Invalid or unsynchronized inventory makes the apply completed-failure only if command termination is conclusive; uncertain process completion takes precedence and returns no usable recovery references. No dependent action may treat that attempt as successful.

Stable saved inputs require the inventory's declared path set to agree with the durably recorded recovery references. Missing/changed declarations or missing/unsafe files block the next dependent command. Cleanup of a failed/interrupted mutator must tolerate missing/partial generated files as already required by 007; it uses the saved command/workspace and does not invent successful recovery references. Successful stop clears that operand's generated-file requirements through core. Restoration uses source-retained inputs in a fresh workspace and its apply publishes a fresh inventory; old mutable markers are not copied.

### Bounds and uncertain completion

- The current attempt's frozen operation timeout bounds normal commands. Every recovery command uses the pending attempt's frozen timeout, regardless of the saved operand's historical timeout or newly loaded configuration; the operand still supplies command/env/workspace. At timeout, Pulltide MUST send termination to the launched process group, allow at most five seconds for exit, then force termination and allow at most five further seconds for exit confirmation. Failure to confirm termination returns `completion-unknown`; no further runtime mutation is permitted.
- Driver outcomes distinguish `completed-success`, `completed-failure`, and `completion-unknown`. A nonzero exit is completed-failure only when termination is established within the restricted foreground profile above; this does not establish termination of escaped descendants. Timeout with confirmed termination is completed-failure. These results describe mutation completion, not health or rollback success.
- After Pulltide process death, an operation whose journal says it may have started MUST be treated as completion-unknown until quiescence is proved. Missing PID, a passed health check, or restarting Pulltide on the same host boot is insufficient. For v0.1 local operations, a changed Linux boot identity establishes that old command processes cannot continue; external or reboot-persistent deployment jobs are prohibited. Without proof, remain recovery-required rather than starting cleanup or restoration.
- Raw stdout and stderr MUST NOT be persisted or exposed in logs/status. Each stream may use at most 64 KiB of transient capture; excess bytes MUST be discarded while draining the stream so output cannot block the command. Diagnostics MUST contain only operation, exit/signal/timeout category and bounded structured identifiers, never arguments, environment values, or raw output.

### Source discovery and external dependency policy

Follow the two-phase source contract in 003 and orchestration in 002. Discovery is a bounded, read-only operation over a staged immutable snapshot. Return the complete repository-relative source-backed input closure before source publication. Never fetch Git or verify Git objects in the runtime adapter. Source validation/publication must succeed before runtime artifact operations; use the published source bytes rather than mutable/ambient inputs. Reference cycles fail discovery. New discovered inputs require a new validated publication before use. Offline source restoration belongs to the source adapter; runtime-specific restoration consumes its fresh workspace and verified retained runtime artifacts without source network fallback.

Exec exposes the entire selected source subtree as source-backed input. It does not infer arbitrary dependencies by executing or parsing operator commands. Permitted host executables and explicit operator-managed application data remain separately validated runtime dependencies under this specification; they are not archived source or permitted alternative definition/build inputs. Read-only discovery MUST NOT execute apply, stop, or health commands.

Relative executable names and relative effective-PATH entries are source-backed lookups and MUST resolve inside the workspace; discover existing referenced source executable blobs (including siblings) through the snapshot before publication. Preserve symlink-before-dot/dot-dot lookup semantics. Missing executable/accessibility still fails preparation before prior stop. Absolute executable/PATH dependencies are explicit operator-managed host tools: they must be accessible regular executable files, without group/other write or set-ID permissions, and MUST NOT select another Pulltide-managed artifact/workspace as a host tool. External application data passed to trusted commands remains operator-managed and is neither inferred nor retained by this adapter. Exec is not a sandbox for arbitrary shell code.

Exec storage admission observes writable private store/workspace context and positive available filesystem blocks/inodes. It does not estimate arbitrary command writes, reserve capacity, or reclaim protected inputs. Actual inventory and core checkpoint write/sync errors remain authoritative.

## Non-goals

Long-running application service supervision, sandboxing untrusted commands, automatic privilege escalation, shell language interpretation, remote deployment jobs, and transactional reversal of arbitrary command side effects. Host tools and external data are operator-managed dependencies; their contents are not archived by saving configuration.

## Failure behavior

A failed prior stop prevents candidate apply and invokes the shared recovery policy. Failed candidate apply or health invokes that policy without advancing last-good. Unknown completion blocks all cleanup and restoration until quiescence is proved. With no last-good deployment, confirmed failed work is cleaned up; cleanup failure or uncertain termination leaves active unknown and recovery-required. Environment changes in the Pulltide parent process MUST NOT change saved execution inputs.

## Acceptance criteria

- **EXEC-01:** Arguments containing spaces or shell metacharacters reach a recording fixture literally unless an explicit shell is selected.
- **EXEC-02:** Changing the parent PATH, HOME, and a same-named environment variable across restart does not change a fixture's saved environment; only the baseline plus saved overrides are present. Its working directory is the retained workspace source path.
- **EXEC-03:** A trace shows preparation, prior stop, then candidate apply. Failed prior stop produces no candidate apply; successful apply followed by failed health never promotes last-good.
- **EXEC-04:** An idempotent service fixture survives replay of stop/apply with exactly one service instance after recovery. This validates Pulltide ordering with a conforming fixture, not arbitrary script idempotency.
- **EXEC-05:** A command ignoring graceful termination receives forced termination after five seconds; confirmation ends within the additional five seconds. An unconfirmed survivor produces completion-unknown and no subsequent mutation.
- **EXEC-06:** Killing Pulltide while a fixture can still mutate resources leaves recovery blocked on same-boot restart, even if its original PID disappears or health passes. After a changed boot identity establishes quiescence, journal recovery can proceed.
- **EXEC-07:** A fixture emits more than 64 KiB per stream, including fake credentials. It does not block on output; transient capture stays within the per-stream limit, and status/logs contain none of the raw output or configured secrets.
- **EXEC-08:** Generated recovery files survive committed completion across power loss; stop tolerates missing/partial files after interrupted apply. Restoration marker lives in a new instance/workspace used by later startup health/stop and protected from GC.
- **EXEC-09:** A timeout of 10, B timeout of 30, and new startup timeout of 60 yield 30 for recovery stop/apply of A; saved A commands/env/workspace remain authoritative.
- **EXEC-10:** Interrupted synchronization before completion yields persistence failure with no dependent command or success; external application-data writes are never claimed restored.

- **EXEC-11:** Read-only discovery returns the selected source subtree without running commands. Source closure/publication failure prevents apply/stop/check invocation. Fresh offline source restoration precedes saved Exec execution; permitted host executables/data follow their separate policy.

- **EXEC-12:** Foreground children that finish before their waiting parent permit completion. A parent that exits leaving a running group member yields completion-unknown and prevents recovery/rollback, even after bounded best-effort termination. Injected signalling/observation failures also yield unknown. No escaped-descendant or general containment guarantee is claimed.
- **EXEC-13:** Every successful apply/restore publishes a fresh version-1 recovery inventory. A valid empty declaration is accepted. Missing, malformed, duplicate, oversized, absolute, traversing, self-referencing, symlinked, hard-linked, wrongly owned/writable, or nonexistent entries fail without publishing usable recovery references. No source-tracked reserved inventory is accepted.
- **EXEC-14:** Inventory/file/directory synchronization failures prevent success and reference publication. Stable inventory/reference disagreement blocks dependent commands. Failed/interrupted cleanup tolerates incomplete inventory, and fresh restoration publishes its own paths before core promotion.
- **EXEC-15:** A harmless synchronous external-service-manager fixture completes its job before return, supports repeated stop/apply, and uses saved working directory/environment. The adapter never treats arbitrary exit status or missing process groups as proof of asynchronous external completion.
